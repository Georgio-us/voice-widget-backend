## Context

Client feedback surfaced several product/data-contract gaps that should be reviewed before implementation. Current goal is to capture the requests and think through backend/data implications without changing code yet.

## 1. Land Plots, Houses, And Sotka Units

Request:
- Support land plots.
- Support houses.
- Land plot area should be expressible in `sotka` (`сотка`) rather than only square meters.
- Houses may have two separate area dimensions:
  - house/building area;
  - land plot area.

Problem:
- Current object model likely treats `area` as one generic square-meter value.
- For houses and land plots, this is insufficient.
- A listing can be a house with `house_area_m2` and `land_area_sotka` at the same time.

Potential data fields:
- `property_type`: `apartment | house | land | commercial`
- `area_m2`: general/current area field, mainly apartment/commercial/building area.
- `land_area_m2`: optional normalized land area in square meters.
- `land_area_sotka`: optional display/filter value for land area in сотки.
- `house_area_m2`: optional explicit house/building area.

Open questions:
- Do we store both `land_area_m2` and `land_area_sotka`, or store one normalized value and format at display time?
- Should filters support land area ranges in sotka?
- Should AI understand phrases like `17 соток`, `участок 6 соток`, `дом 120 м2 на 5 сотках`?

## 2. Ukrainian Localization For Districts On Cards

Request:
- District names shown on property cards must be localized to Ukrainian.
- Current cards show Russian district names, e.g. `Киевский`, `Приморский`.
- Ukrainian UI should show Ukrainian labels, e.g. `Київський`, `Приморський`, etc.

Problem:
- District labels appear to be stored/rendered as Russian strings.
- The issue is specifically about labels displayed on property cards, not necessarily the canonical internal value.

Recommended direction:
- Keep internal canonical district values stable.
- Add UI label mapping by active language.
- Do not mutate stored DB values just for localization.

Potential mapping:
- `Киевский` -> `Київський`
- `Приморский` -> `Приморський`
- `Малиновский` -> `Малиновський` or current official district naming if product uses updated naming.
- `Суворовский` -> `Суворовський` or current official district naming if product uses updated naming.

Open questions:
- Which district naming standard do we use: legacy Odessa district names or updated administrative names?
- Should card labels follow the UI language toggle only, or client default language?

## 3. Default Bot Language / Ukrainian-First Behavior

Request:
- Bot sometimes switches between Ukrainian and Russian during the dialog.
- Desired behavior: default to Ukrainian unless the user explicitly chooses Russian in UI.
- The bot should not answer in Russian merely because the user uses mixed language or because ASR/prompt drifts.

Problem:
- Current language detection may use detected speech/text language.
- That can override the UI language preference and produce mixed-language dialogs.

Potential rule:
- `uiLanguage` or explicit frontend language selection has priority.
- If user selected `UA`, assistant must answer in Ukrainian.
- If user selected `RU`, assistant may answer in Russian.
- If no explicit selection exists, default to Ukrainian for this client/product context.

Implementation areas:
- Frontend language toggle payload.
- Backend request handling: `req.body.lang` / session language.
- System prompt language rule.
- Session persistence of selected language.

Open questions:
- Is this Ukrainian-first behavior global or client-specific?
- Do we need a Railway/env flag such as `DEFAULT_ASSISTANT_LANG=uk`?
- Do we need `LOCK_ASSISTANT_LANG_TO_UI=1`?

## 4. Government Programs / State Programs

Request:
- Add support for government programs as a listing/filter property.
- Examples:
  - `єОселя`
  - `єВідновлення`
  - state programs / vouchers.
- Users should be able to ask for objects eligible for these programs.
- Realtors/admins should be able to mark listings as eligible when adding/editing objects.
- OLX import should preserve this field if OLX exposes it.

Concept:
- General field: `government_programs` / `state_programs`.
- Specific values under it: `eoselia`, `evidnovlennia`, possibly more later.

Potential backend model:
- Boolean general flag: `has_government_programs`.
- Array enum field: `government_programs: ['eoselia', 'evidnovlennia']`.

Potential AI behavior:
- User says `госпрограмма`, `держпрограма`, `єОселя`, `єВідновлення`, `сертификат`, `ваучер`.
- Backend/AI maps this to a filter:
  - generic state program request -> any government program.
  - specific program request -> exact program.

Implementation areas:
- DB schema / JSON features field.
- Manual add/edit object form.
- Manual filters UI.
- AI extraction schema and prompt.
- Search/filter logic.
- OLX mapper.
- Future XML/Nero/RAM import mappers.

Open questions:
- Should generic `state program` include all programs or only selected ones?
- Is `voucher` always `єВідновлення`, or can it mean another certificate/program?
- Does OLX provide structured fields for these programs, or only text badges/descriptions?

## 5. Lead Notification: Object Link And Object Summary

Request:
- When a user submits a lead from a specific object, the realtor/admin should understand which exact object the user referred to.
- Current lead notification may include only object ID such as `SEED006`, which is not enough.
- Desired:
  - object ID as a clickable link;
  - concise object summary in the lead notification.

Example desired summary:
- `SEED006`
- `Продажа квартиры, Киевский район, 2 комнаты, 55 000 USD`
- Link opens the object/card/details/admin view if possible.

Potential data included in lead payload/notification:
- `property_id`
- `property_url` or miniapp deep link
- `title`
- `operation`
- `property_type`
- `district`
- `rooms`
- `area`
- `price`
- maybe `residential_complex`

Implementation areas:
- Lead submission frontend payload.
- Backend lead endpoint.
- Telegram/project notification formatter.
- Admin panel lead details.
- Miniapp deep-link route or object details route.

Open questions:
- What URL should object links use?
- Can Telegram notification deep-link directly into Mini App object details?
- Do we already have a stable route/card ID URL for object detail?
- Should lead summary be localized by client language?

## 10. Government Programs UX V1

Scope:
- Add only the visible checkbox flow first.
- Manual filters should expose one checkbox:
  - UA: `Держпрограми`
  - RU: `Госпрограммы`
- Manual add/edit object step 2 should expose the same logical checkbox.

Current local implementation note:
- Manual filters expose only the broad user-facing checkbox:
  - UA: `Держпрограми`
  - RU: `Госпрограммы`
- Manual add/edit exposes specific program checkboxes:
  - `єОселя`
  - `єВідновлення`
- Internal contract:
  - if either specific checkbox is enabled, the object is treated as `governmentProgram=true`;
  - `governmentPrograms` stores specific program tokens (`eoselia`, `evidnovlennia`);
  - broad search by `governmentProgram=true` returns both specific program groups.
- Relaxed behavior:
  - `governmentProgram`, `eoselia`, and `evidnovlennia` are hard gates;
  - relaxed mode may soften other filters such as price/area/rooms according to the existing mechanism;
  - relaxed mode must not show listings outside the requested government-program layer.

Next decision:
- Decide how OLX import should map government-program badges/fields into the same `features` contract.

- Decomposition completed and smoke-tested.
