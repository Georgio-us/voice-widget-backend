# Фаза 2 Current Execution (текущее исполнение)

Документ фиксирует **фактическое состояние** после итераций Phase 2 вокруг AI → фильтры каталога, в формате, согласованном с `PHASE1_FINALIZATION.md`. Это не «to-be» контракт целиком, а **снимок того, что уже в коде и зачем**.

---

## 1. Наследие Phase 1 и что изменилось в Phase 2

### Canonical path (без изменений по смыслу)
1. `insights` — `UnderstandingManager.export()` или явный `insightsSource` при обновлении каталога.
2. `buildCanonicalAiPatch(insights)` — `Voice-Widget-Frontend/voice-widget-v1.js`.
3. Слияние с ручными оверрайдами в `getCatalogEffectiveSearchParams(...)`.
4. Сбор запроса в `refreshCatalogByEffectiveQuery(...)`.
5. `/api/cards/search` через `api.fetchCardsSearch(requestQuery)`.

### Отличия от Phase 1 Contract (по факту кода)
- В Phase 1 в документе `operation` и `type` были в списке **Restricted** (AI auto-commit forbidden). В Phase 2 для продукта нужна возможность **один раз зафиксировать** сделку и тип из AI/голоса, без «перещёлкивания» на каждом шаге.
- Реализована **политика замков (Smart lock)** + сбросы при конфликте и смене сессии (см. §2).

## 2. Политика `operation` / `type` (замки и сбросы)

### Зачем
- Защита от хаотичной смены `sale`/`rent` и `apartment`/… от шума LLM после того, как пользователь уже зафиксировал режим.
- Учёт того, что WebView Telegram может **сохранять память** виджета между «обновлениями» бота без полного сброса JS.

### Как работает (кратко)
- `_catalogAiLockedOperation`, `_catalogAiLockedType` — последние явно применённые значения.
- В `getCatalogEffectiveSearchParams`: если патч текущего хода **противоречит** замку по `operation` или `type`, соответствующий замок **сбрасывается** (новый явный intent AI выигрывает над устаревшим замком).
- При смене `sessionId` в `_setSessionIdAndDisplay` оба замка **обнуляются**.
- После успешного merge замки обновляются в `refreshCatalogByEffectiveQuery` из `buildCanonicalAiPatch` и ручных оверрайдов (не из «голого» дефолта после вырезания полей).

### Приоритет
- **Ручные фильтры > AI** для тех же полей (как в Phase 1).

## 3. Порядок обновления understanding и каталога

### Проблема
Раньше вызывалось `syncBackendDrivenState` → `ingestBackendCatalogPayload` → merge с `understanding.export()` **до** `understanding.update(data.insights)`, из-за чего каталог мог строиться на **старом** export.

### Исправление
После ответа API (текст и аудио): сначала **`understanding.update(data.insights)`**, затем **`syncBackendDrivenState(data)`** (внутри — каталог).

## 4. Цены: две шкалы (аренда / продажа) и snapping

### UI (ручные фильтры)
- В `buildFilterPickerOptions` для `priceMin` / `priceMax` две шкалы:
  - **Аренда (`rent`)**: шаги 100…1000, затем 1200…3000 с шагом 200 (как договорено в сессии).
  - **Продажа (`sale`)**: прежняя шкала в тысячах USD (шаги из area-scale × 1000).
- При переключении «Аренда / Продажа» в оверлее фильтров селекты цен **пересобираются** под выбранный режим.

### AI → execution
- В `buildCanonicalAiPatch`: функция **snapping** бюджета к ближайшей точке шкалы текущей операции.
- **Продажа + сумма < 5000 USD** в бюджете — значение **не коммитится** (защита от ошибок Whisper вроде «1100» при продаже).
- Для верхней границы диапазона — округление **вверх** к ближайшей точке шкалы (не сужать выдачу); для нижней — **вниз** (по согласованию в сессии).
- Правило **70%** от max при отсутствии min для strict-flow **сохранено**.

## 6. ЖК «Альтаир» vs маркер «таир» (Таирова)

### Контекст
- Маркеры **`таир` / `tairo`** в правилах Киевского района и «похоже на район» нужны в т.ч. для **Таировой** (местность), а не только для слова «Киевский».
- Подстрока «таир» в **«Альтаир» / «Аль-Таир»** давала ложное попадание в Киевский bucket.

### Текущее правило (frontend)
- Маркеры **`киев|kiev|kyiv|таир|tairo`** для Киевского **возвращены** как раньше.
- Перед ними добавлено **узкое исключение**: токены вида **`аль…таир` / `альтаир`** (ЖК) **не** считаются районным маркером «таир»:
  - в `normalizeDistrictSlug` — возврат пустого slug (не `kievsky`);
  - в `isDistrictLikeLocation` — `false` для таких строк;
  - в `_normalizeDistrictForRelax` — возврат исходной строки без маппинга в `kievsky`.

### Ограничение (честно)
Различение **«Киев как город»** vs **«Киевский район Одессы»** по одной строке без контекста продукта **не решено** этим документом; продукт ориентирован на **Одессу**. Отдельная политика disambiguation — вне scope этого снимка.

## 7. Промпт и схема извлечения (backend)

### Файлы
- `Voice-Widget-Backend/services/personality.js` — `BASE_SYSTEM_PROMPT`: типы недвижимости, `rcOnly`, паркинг, балкон/лоджия, Аркадия, центр, смарт; нормализация названий районов в подсказках; правило для **«Аль-Таир» → «Альтаир»** в тексте промпта.

### Frontend fallback
- В `buildCanonicalAiPatch` остаётся строковая подмена **`Аль-Таир` → `Альтаир`** для `residentialComplex`, даже если модель ошиблась.
