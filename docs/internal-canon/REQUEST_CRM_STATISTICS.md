# Request CRM Statistics

## 1) Цель документа
Зафиксировать поэтапный план развития раздела `Статистика` в админ-панели:
- что уже можем показывать из текущих данных без рефакторинга,
- какие поля можно дотянуть малой доработкой,
- какие задачи требуют расширения схемы данных/миграций.

Документ аналитический. Внедрение выполняется по фазам.

---

## 2) Текущий AS-IS (по данным и источникам)

### 2.1 Уже доступно и используется
- `users`:
  - общее число пользователей бота,
  - новые пользователи за сегодня.
- `lead_requests`:
  - общее число заявок,
  - новые заявки за сегодня,
  - последние заявки (по `created_at DESC`).
- `session_logs`:
  - общее число сессий,
  - новые сессии за сегодня.
- `properties`:
  - активные объекты.

### 2.2 Что уже отфильтровано в статистике
- legacy-источники `widget_*` исключаются из CRM-среза заявок
  (исторический контур до Telegram).

### 2.3 Важные нюансы текущего контура
- В `lead_requests` часть Telegram-данных хранится в `extra` (json):
  - `telegramUsername`,
  - `tgUserId` (если передан).
- `session_id` у лида есть, значит можно связывать лид с `session_logs`.
- Email может быть автосгенерирован как fallback (`...@telegram.local`) в старой логике.

---

## 3) Scope (что подтверждено бизнесом)

### 3.1 Ближайший приоритет
Показывать в блоке последних лидов:
- понятную идентификацию клиента,
- кликабельный Telegram-переход (если есть username или tg id),
- контакты (телефон/email) только если реально предоставлены пользователем.

### 3.2 Подтвержденные правила
- Если email не введен пользователем вручную, показывать email нельзя.
- Если телефон не введен, телефон не показывать.
- Если есть Telegram username/tg id, дать быстрый переход в диалог.

---

## 4) Фазовый план внедрения

## Фаза A (быстрый слой, без рефакторинга БД)
Цель: улучшить `Последние заявки` в существующем блоке `Статистика`.

### A.1 Показ полей
- Дата/время заявки.
- Имя.
- Источник (человекочитаемый label).
- `property_id` (если есть).
- Telegram:
  - если есть username: ссылка `https://t.me/<username>`,
  - иначе если есть tg id: ссылка `tg://user?id=<id>`.
- Телефон/email: только если реально есть в записи.

### A.2 Нормализация отображения
- Словарь для `source`:
  - `tg_property_card`,
  - `tg_header_main`,
  - `guest_want_bot_trial`,
  - `guest_want_bot_consult`,
  - и т.д.
- Скрывать legacy `widget_*` (уже сделано в текущем CRM-срезе).

### A.3 Ограничения Фазы A
- Без отдельной карточки клиента.
- Без отдельной таблицы профиля клиента.
- Без AI-summary (только raw/derived поля).

---

## Фаза B (детализация лида, still без глубокой миграции)
Цель: добавить “детали лида” (popup/accordion/модалка — решение позже).

### B.1 Что выводим в деталях
- Основные контакты (telegram/phone/email).
- `session_id`.
- Последний запрос пользователя (транскрипция/текст из session logs).
- Извлеченные инсайты (если есть).
- Последний показанный объект (если есть).

### B.2 Технически
- JOIN по `lead_requests.session_id` -> `session_logs.session_id`.
- Парсинг последних `messages[].meta.insights` и user-message.

---

## Фаза C (карточка клиента / mini CRM)
Цель: единая сущность клиента и история взаимодействия.

### C.1 Планируемые блоки
- Профиль клиента.
- История заявок.
- История запросов/интентов.
- Конверсионные действия (просмотры, шаринг, оставление заявок).

### C.2 Потенциальные варианты UI
- Аккордеон в статистике.
- Модальное окно “Клиент”.
- Отдельная сущность меню “Клиенты”.

Решение по UX принимается после Фазы A/B на основе реальных данных.

---

## 5) Что можно дотянуть без изменений схемы БД
- Telegram username/tg id (из `lead_requests.extra`, если передано).
- Контактные поля из `lead_requests`.
- История запроса через `session_id` и `session_logs`.
- Источник лида и привязка к объекту (`property_id`).

---

## 6) Что потребует миграций/SQL (кандидаты на отдельный этап)

Ниже список не для немедленного внедрения, а для будущей стабилизации CRM-контура:

1. Явные колонки в `lead_requests`:
- `telegram_username` (text),
- `telegram_user_id` (bigint),
- `is_email_user_provided` (bool),
- `is_phone_user_provided` (bool).

2. Запрет автогенерации email fallback:
- убрать генерацию `@telegram.local` в createLead,
- или хранить флаг `email_generated`.

3. Материализованный слой для аналитики (опционально):
- агрегаты по клиентам/лидам/источникам,
- top intents, top viewed objects, time-to-lead.

4. Индексы под CRM-витрины:
- `lead_requests(client_id, created_at desc)`,
- `lead_requests(client_id, source, created_at desc)`,
- `lead_requests(session_id)`,
- `session_logs(session_id)`.

---

## 7) Риски и контроль качества
- Исторические данные могут быть неоднородны (legacy источники, пустые поля).
- В старых лидах Telegram-поля могут отсутствовать.
- Нужна явная маркировка “нет данных”, а не подстановка фиктивных значений.

Критерии качества для Фазы A:
- `Последние заявки` действительно отсортированы по дате убыванию.
- Не показываются legacy `widget_*`.
- Кликабельный Telegram работает, если есть username/tg id.
- Email показывается только если введен пользователем.
